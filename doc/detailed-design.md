# SaaS 多租户 Chatbot 系统详细设计文档

## 1. 文档信息

| 项目 | 内容 |
| --- | --- |
| 文档名称 | SaaS 多租户 Chatbot 系统详细设计文档 |
| 输入文档 | `doc/proposal.md`、`doc/high-level-design.md` |
| 设计范围 | 全量范围：MVP、二期能力、长期扩展预留 |
| 目标读者 | 前后端联合开发、联调与测试协作人员 |
| 模块组织方式 | 按业务域划分 |
| 编写原则 | 模块职责单一、边界清晰、可独立测试、未确认事项显式标记 |

## 2. 设计目标

1. 将需求文档中的业务能力拆分为可独立实现、可独立测试的业务模块。
2. 明确前后端边界、模块依赖、数据归属和核心处理流程。
3. 优先保证多租户数据隔离、配置复用、异步任务解耦和审计可追踪。
4. 在不破坏 MVP 简洁性的前提下，为二期实时人工客服和工单能力预留清晰扩展点。

## 3. 设计原则

### 3.1 模块独立原则

1. 每个模块只负责一个稳定业务域。
2. 模块对外只暴露明确的服务接口和数据契约，不直接依赖上游页面实现。
3. 模块间通过领域服务调用、异步任务或只读查询协作，避免共享可变状态。
4. 每个模块均可进行：单元测试、接口测试、权限测试、租户隔离测试。

### 3.2 统一约束

1. 所有租户业务数据必须绑定 `tenant_id`。
2. 所有后台请求的租户范围必须来自认证上下文，而非客户端自由传参。
3. 网站插件与独立聊天页共享同一份 chatbot 配置。
4. 文件解析、网页抓取、向量生成均采用异步任务，避免阻塞交互链路。
5. 关键操作必须进入审计链路。

## 4. 总体设计

### 4.1 逻辑分层

1. **接入层**：`tenant-admin`、`super-admin`、`chatbot-widget`、`chat-page`。
2. **业务服务层**：认证权限、租户管理、套餐额度、chatbot 配置、FAQ、知识库、对话编排、模型调用、会话记录、统计、审计、二期客服、二期工单。
3. **任务处理层**：文件解析任务、网页抓取任务、文本切分任务、向量生成任务。
4. **数据存储层**：PostgreSQL、pgvector、本地文件存储。
5. **外部依赖层**：模型供应商 API、公开网页抓取目标站点。

### 4.2 前端应用分工

| 应用 | 核心职责 | 主要依赖模块 |
| --- | --- | --- |
| `tenant-admin` | 租户运营后台、chatbot 配置、知识库管理、会话与统计 | Auth、User、Chatbot、FAQ、Knowledge、Conversation、Analytics、Plan |
| `super-admin` | 平台租户、套餐、模型供应商、监控与审计 | Auth、Tenant、Plan、Model Provider、Analytics、Audit |
| `chatbot-widget` | 网站插件聊天入口 | Deployment、Chat、Conversation |
| `chat-page` | 独立聊天页入口 | Deployment、Chat、Conversation |

### 4.3 模块依赖规则

1. 认证权限模块是所有后台模块的公共前置依赖。
2. 租户管理和套餐额度模块是租户级业务模块的基础依赖。
3. Chatbot 配置模块是 FAQ、知识库、渠道部署、对话编排的基础依赖。
4. 对话编排模块可调用 FAQ、知识库、模型调用，但不反向被这些模块依赖业务决策。
5. 会话记录、统计报表、审计日志优先作为结果记录模块，不反向承载业务主流程判断。

## 5. 公共设计约束

### 5.1 身份与租户上下文

1. 超级管理员与租户后台用户使用独立登录入口。
2. 登录成功后生成后台访问令牌，令牌中包含用户 ID、角色集合、租户范围、用户类型。
3. 访客侧匿名会话不进入后台用户体系，只生成匿名访客标识。
4. 后端统一从认证上下文解析 `tenant_id`，租户端控制器不得信任外部传入的租户标识。

### 5.2 状态模型约定

建议统一使用显式状态机，避免布尔字段扩散：

1. `Tenant.status`：启用、禁用。
2. `Chatbot.status`：草稿、启用、停用、删除。
3. `FAQ.status`：启用、停用、删除。
4. `KnowledgeSource.status`：待处理、处理中、成功、失败、停用。
5. `Conversation.status`：进行中、已结束、待跟进、已删除。
6. `HandoffRecord.status`：待跟进、处理中、已关闭。
7. `AgentSession.status`：排队中、服务中、已结束。
8. `Ticket.status`：待处理、处理中、已解决、已关闭。

### 5.3 异步任务约定

1. 文件解析、网页抓取、向量生成必须拆为可重试任务。
2. 任务状态、失败原因、重试次数必须可查询。
3. 任务执行结果必须回写到业务实体，避免前端轮询无状态任务。

### 5.4 国际化约定

1. 前端界面文案统一采用 i18n 资源管理。
2. FAQ、欢迎语、兜底话术、系统提示词允许按语言维度配置。
3. chatbot 回复语言优先级：用户输入语言识别结果 > chatbot 默认回复语言 > 系统默认语言。

## 6. 模块详细设计

## 6.1 认证与权限模块

### 6.1.1 模块职责

1. 支持租户端与超级管理员端邮箱密码登录。
2. 支持退出登录、忘记密码、重置密码。
3. 管理后台用户、角色、权限矩阵。
4. 为其他后台模块提供统一鉴权和授权能力。
5. 实现登录失败频率限制和密码安全存储。

### 6.1.2 边界与依赖

1. 仅负责后台用户身份体系，不负责匿名访客身份。
2. 不负责租户业务数据查询，只提供租户访问上下文。
3. 依赖租户管理模块校验租户状态。
4. 依赖审计日志模块记录登录、退出、重置密码等敏感操作。

### 6.1.3 数据设计

核心实体：`User`、`Role`、`Permission`、`Tenant`。

关系约束：

1. 一个租户可拥有多个后台用户。
2. 一个后台用户可绑定多个角色。
3. 角色与权限采用多对多关系。
4. 超级管理员用户与租户后台用户应通过用户类型或独立作用域区分。

### 6.1.4 核心流程

1. 用户提交邮箱密码。
2. 系统校验账户存在性、密码哈希、账户状态、租户状态。
3. 系统检查登录失败次数与限频规则。
4. 登录成功后签发访问令牌并写入审计日志。
5. 后续请求由鉴权中间件完成身份解析与角色校验。

### 6.1.5 API 设计

1. 认证接口：登录、退出、发起密码重置、执行密码重置。
2. 用户接口：成员创建、编辑、禁用、重置密码。
3. 权限接口：角色列表、角色分配、权限矩阵查询。

### 6.1.6 异常处理

1. 账户不存在与密码错误统一返回模糊错误，避免账户枚举。
2. 达到限频阈值时返回限流提示。
3. 租户被禁用时拒绝登录。
4. 权限不足时返回统一未授权错误。

### 6.1.7 测试点

1. 正常登录、退出、重置密码。
2. 密码错误限频。
3. 禁用用户与禁用租户无法登录。
4. 不同角色的页面与接口访问隔离。
5. 超级管理员与租户后台用户作用域隔离。

## 6.2 租户管理模块

### 6.2.1 模块职责

1. 超级管理员创建、编辑、启用、禁用租户。
2. 创建租户管理员账号。
3. 维护租户联系人、备注、当前状态。
4. 为其他模块提供租户基础信息与状态校验。

### 6.2.2 边界与依赖

1. 只面向超级管理员端开放。
2. 不承载套餐额度逻辑，套餐分配由套餐模块负责。
3. 被 chatbot、会话、统计、对话编排模块用于租户状态前置校验。
4. 依赖审计日志模块记录关键变更。

### 6.2.3 数据设计

核心实体：`Tenant`、`User`。

关系约束：

1. 一个租户至少应存在一个租户管理员。
2. 租户状态变更需要影响 chatbot 新会话创建与后台访问。

### 6.2.4 核心流程

1. 超级管理员创建租户。
2. 系统生成租户记录并创建初始租户管理员。
3. 超级管理员后续修改租户状态。
4. 下游模块在关键操作前读取租户状态，决定是否允许继续执行。

### 6.2.5 API 设计

1. 租户创建与编辑接口。
2. 租户状态变更接口。
3. 租户详情、列表、异常概览接口。

### 6.2.6 异常处理

1. 重复租户名称按平台规则拒绝或提示。
2. 禁用租户时必须阻止新增会话和后台关键写操作。
3. 删除租户不建议在 MVP 提供物理删除，仅建议禁用。

### 6.2.7 测试点

1. 创建租户与初始管理员成功。
2. 租户禁用后租户端无法继续关键操作。
3. 超级管理员可查看租户基础状态与用量摘要。

## 6.3 套餐额度与用量模块

### 6.3.1 模块职责

1. 管理套餐模板。
2. 为租户分配套餐并支持租户级额度覆盖。
3. 对机器人数量、消息量、知识库容量、文件数量、Token 用量进行前置校验。
4. 记录用量消耗并提供统计口径。

### 6.3.2 边界与依赖

1. 套餐定义由超级管理员维护，租户端只读查看。
2. 不直接执行业务操作，只返回“允许/拒绝 + 原因”。
3. 被 chatbot、知识库、对话编排、模型调用等模块复用。

### 6.3.3 数据设计

核心实体：`Plan`、`TenantQuota`、`UsageRecord`、`Tenant`。

关系约束：

1. 一个租户应绑定一个当前生效套餐。
2. `TenantQuota` 用于覆盖套餐默认额度，而非复制整套套餐定义。
3. `UsageRecord` 需标记消耗来源，如消息、文件、向量、模型调用。

### 6.3.4 核心流程

1. 业务模块发起额度校验请求。
2. 套餐模块读取租户套餐与租户级覆盖额度。
3. 模块根据资源类型判断是否超限。
4. 若未超限，业务模块执行操作并回写实际消耗。
5. 若超限，直接返回具体限制项。

### 6.3.5 API 设计

1. 套餐创建、编辑、启停接口。
2. 租户套餐分配接口。
3. 租户额度调整接口。
4. 租户额度与用量查询接口。

### 6.3.6 异常处理

1. 套餐未分配时租户不可进入正式运营状态。
2. 额度超限需明确返回超限资源类型。
3. 消耗回写失败时必须进入补偿或告警机制，避免用量失真。

### 6.3.7 测试点

1. 不同资源类型超限拦截。
2. 套餐默认额度与租户覆盖额度叠加生效。
3. 并发消息消耗下的额度一致性。

## 6.4 Chatbot 配置模块

### 6.4.1 模块职责

1. 管理 chatbot 基础信息。
2. 管理外观配置。
3. 管理行为策略配置。
4. 支持复制 chatbot 配置。
5. 向用户端提供统一配置快照。

### 6.4.2 边界与依赖

1. 只负责 chatbot 配置，不负责 FAQ/知识数据内容。
2. chatbot 的部署入口由渠道部署模块负责。
3. 依赖套餐模块进行 chatbot 数量校验。
4. 被 FAQ、知识库、对话编排、渠道部署模块依赖。

### 6.4.3 数据设计

核心实体：`Chatbot`、`ChatbotAppearance`、`ChatbotBehavior`、`Tenant`。

关系约束：

1. 一个 chatbot 只属于一个租户。
2. 一个 chatbot 对应一份外观配置和一份行为策略配置。
3. 复制 chatbot 时复制配置，不复制会话记录与历史用量。

### 6.4.4 核心流程

1. 租户用户创建 chatbot。
2. 系统校验套餐数量上限。
3. 创建 chatbot 主体、默认外观、默认行为策略。
4. 租户继续编辑欢迎语、头像、文案、风格、提示词等配置。
5. 启用后的配置被 widget 与 chat-page 同步复用。

### 6.4.5 API 设计

1. chatbot 列表、详情、创建、编辑、启停、删除、复制接口。
2. 外观配置保存与预览接口。
3. 行为策略保存与读取接口。
4. 对外配置快照读取接口。

### 6.4.6 异常处理

1. 停用 chatbot 后禁止新会话，但允许查看历史会话。
2. 删除 chatbot 建议采用逻辑删除，避免历史记录丢失。
3. 复制 chatbot 时若超出套餐数量上限则拒绝执行。

### 6.4.7 测试点

1. 创建、编辑、启停、复制 chatbot。
2. 外观与行为配置保存后对两类入口同时生效。
3. 停用 chatbot 后新会话禁止创建。

## 6.5 渠道部署模块

### 6.5.1 模块职责

1. 生成网站插件嵌入代码。
2. 生成独立聊天页链接。
3. 管理允许嵌入域名白名单。
4. 校验用户端入口合法性。

### 6.5.2 边界与依赖

1. 不负责对话内容生成，只负责入口配置与安全校验。
2. 依赖 chatbot 配置模块获取 chatbot 状态与对外配置。
3. 被 `chatbot-widget`、`chat-page`、对话编排模块调用。

### 6.5.3 数据设计

核心实体：`Chatbot`、部署配置子对象或独立部署配置实体。

关系约束：

1. 一个 chatbot 可关联多个白名单域名。
2. 网站插件与独立聊天页共享同一个 chatbot 标识。

### 6.5.4 核心流程

1. 租户在后台查看部署配置。
2. 系统生成嵌入脚本和独立聊天页链接。
3. 插件初始化时携带 chatbot 标识与当前域名。
4. 后端校验 chatbot 状态、租户状态、域名白名单。
5. 校验通过后返回配置与会话初始化能力。

### 6.5.5 API 设计

1. 部署信息查询接口。
2. 白名单域名管理接口。
3. 访客入口初始化校验接口。

### 6.5.6 异常处理

1. 未授权域名拒绝加载插件配置。
2. chatbot 停用或租户禁用时拒绝新会话。
3. 非法 chatbot 标识统一返回无效入口错误。

### 6.5.7 测试点

1. 白名单域名生效验证。
2. 非白名单域名拦截。
3. 插件与独立聊天页共享同一配置快照。

## 6.6 规则问答模块

### 6.6.1 模块职责

1. 管理 FAQ 条目。
2. 支持手工录入、批量导入、导出、启停、删除、搜索。
3. 在对话编排中提供优先级最高的规则匹配能力。

### 6.6.2 边界与依赖

1. 仅处理结构化问答，不负责向量检索。
2. 依赖 chatbot 模块确定 FAQ 归属。
3. 被对话编排模块以同步方式调用。

### 6.6.3 数据设计

核心实体：`FAQ`、`Chatbot`。

关系约束：

1. FAQ 必须绑定 chatbot。
2. FAQ 应包含主问题、相似问法、答案、语言、状态。
3. FAQ 删除建议采用逻辑删除，便于审计和恢复。

### 6.6.4 核心流程

1. 租户维护 FAQ 条目。
2. 对话编排收到用户问题后先调用 FAQ 匹配。
3. 若命中，直接返回规则答案并记录命中详情。
4. 若未命中，继续进入知识库检索流程。

### 6.6.5 API 设计

1. FAQ 列表与搜索接口。
2. FAQ 创建、编辑、启停、删除接口。
3. FAQ 导入与导出接口。
4. FAQ 匹配服务接口。

### 6.6.6 异常处理

1. 导入格式错误需返回逐条失败原因。
2. 停用 FAQ 不参与匹配。
3. 语言不一致时应只在匹配策略允许范围内参与候选。

### 6.6.7 测试点

1. FAQ CRUD 与导入导出。
2. 启用状态 FAQ 优先命中。
3. 未命中时正确流转到知识库/模型流程。

## 6.7 知识库模块

### 6.7.1 模块职责

1. 管理文件型和网页型知识来源。
2. 保存原始文件元数据与抓取元数据。
3. 执行文本解析、切分、向量生成、向量入库。
4. 为对话编排提供按租户与 chatbot 范围限定的检索结果。

### 6.7.2 边界与依赖

1. 文件与网页导入属于知识库模块。
2. 向量生成依赖模型调用模块，不在知识库内实现模型适配。
3. 额度校验依赖套餐模块。
4. 被对话编排模块只读调用。

### 6.7.3 数据设计

核心实体：`KnowledgeSource`、`KnowledgeChunk`、`Chatbot`、`ModelCallLog`。

关系约束：

1. 一个知识来源属于一个 chatbot。
2. 一个知识来源可拆分为多个知识片段。
3. 每个知识片段必须保留来源信息，用于回答引用展示。

### 6.7.4 核心流程

#### 文件上传流程

1. 租户上传文件。
2. 系统校验文件类型、大小、套餐额度、租户归属。
3. 保存原始文件到租户隔离目录。
4. 创建解析任务并将来源状态置为待处理。
5. 异步任务解析文本、切分片段、生成向量、写入 pgvector。
6. 更新来源状态为成功或失败。

#### 网页抓取流程

1. 租户提交 URL。
2. 系统校验 URL 合法性、租户权限和抓取频率。
3. 抓取正文内容并保存源数据。
4. 执行切分、向量生成、入库。
5. 支持重新抓取并保留最新抓取状态。

#### 检索流程

1. 对话编排提交问题与 chatbot 范围。
2. 知识库模块按 `tenant_id`、`chatbot_id` 过滤候选片段。
3. 执行向量检索并返回相关片段。
4. 返回片段摘要、来源标题、来源链接、相似度分数。

### 6.7.5 API 设计

1. 文件上传与列表接口。
2. 文件状态查询与重试接口。
3. 网页来源创建、重抓、停用接口。
4. 知识来源列表与详情接口。
5. 检索服务接口。

### 6.7.6 异常处理

1. 不支持的文件类型直接拒绝上传。
2. 文件超限、容量超限、文件数量超限时给出具体原因。
3. 解析失败、抓取失败、向量生成失败需记录失败原因并允许重试。
4. 无权限网页或超频抓取应明确拒绝。

### 6.7.7 测试点

1. 各文件类型上传与解析。
2. 文件失败重试与状态回写。
3. 网页抓取成功、失败、重抓。
4. 检索结果严格限定在当前租户和 chatbot 下。
5. 解析后的引用来源可回溯。

## 6.8 对话编排模块

### 6.8.1 模块职责

1. 管理匿名会话生命周期。
2. 编排 FAQ、知识库检索和大模型回答流程。
3. 输出用户端所需的回答、引用来源、错误提示、反馈入口。
4. 无法回答时生成待跟进记录。

### 6.8.2 边界与依赖

1. 仅负责聊天主流程编排，不负责具体 FAQ 匹配算法或向量检索实现。
2. 依赖渠道部署模块校验入口合法性。
3. 依赖租户、chatbot、套餐模块完成前置校验。
4. 依赖 FAQ、知识库、模型调用模块生成结果。
5. 依赖会话记录模块或持久化层写入消息结果。

### 6.8.3 数据设计

核心实体：`Conversation`、`Message`、`HandoffRecord`、`ModelCallLog`、`Chatbot`。

关系约束：

1. 一个匿名访客可产生多个会话。
2. 一个会话包含多条访客消息与机器人消息。
3. 一次模型调用可关联一条机器人回复消息。
4. 待跟进记录应关联会话与访客联系方式。

### 6.8.4 核心流程

1. 入口校验：域名、chatbot 状态、租户状态、额度状态。
2. 初始化会话：生成匿名访客 ID、会话 ID，记录入口来源、浏览器信息、IP、时间。
3. 用户发送消息后先记录访客消息。
4. 调用 FAQ 模块进行规则匹配。
5. FAQ 未命中时调用知识库检索。
6. 若检索命中，带片段上下文调用模型生成回答。
7. 若检索未命中，按行为策略决定是否直接调用模型。
8. 记录回答消息、模型调用日志、知识引用、反馈能力。
9. 若回答失败或无法覆盖问题，返回兜底话术并可创建待跟进记录。

### 6.8.5 API 设计

1. 会话初始化接口。
2. 消息发送接口。
3. 访客反馈提交接口。
4. 待跟进信息提交接口。

### 6.8.6 异常处理

1. chatbot 停用、租户禁用、额度不足时直接拒绝新消息处理。
2. FAQ、检索、模型任一环节失败时必须返回统一兜底结果。
3. 模型调用超时应允许返回“处理中/稍后重试”或兜底话术。
4. 重复提交消息需有幂等控制或最小化重复影响。

### 6.8.7 测试点

1. 匿名会话创建与多轮对话。
2. FAQ 命中链路。
3. 知识库命中链路。
4. 知识未命中但允许大模型直答链路。
5. 错误兜底与待跟进记录链路。
6. 引用来源展示与访客反馈提交流程。

## 6.9 模型供应商与模型调用模块

### 6.9.1 模块职责

1. 管理模型供应商接入配置。
2. 提供统一模型调用适配层。
3. 同时服务于对话回答与向量生成场景。
4. 记录 Token 用量、成本估算、失败率与错误明细。

### 6.9.2 边界与依赖

1. 供应商配置由超级管理员管理，租户端只能在授权范围内选择。
2. 模型调用模块不决定业务策略，只执行调用并返回结构化结果。
3. 依赖套餐模块校验可用模型范围与 Token 上限。

### 6.9.3 数据设计

核心实体：`ModelProvider`、`ModelCallLog`、`Plan`、`TenantQuota`。

关系约束：

1. 模型供应商可挂载多个模型定义。
2. 模型调用日志需可关联租户、chatbot、会话、用途类型。
3. 成本估算应基于调用时单价快照，避免后续单价变更影响历史统计。

### 6.9.4 核心流程

1. 超级管理员维护供应商与模型配置。
2. 业务模块发起统一调用请求，声明用途：聊天回答或向量生成。
3. 模型模块根据租户授权与默认配置选择具体模型。
4. 执行调用、重试、超时控制。
5. 写入调用日志与 Token 成本数据。

### 6.9.5 API 设计

1. 供应商配置管理接口。
2. 模型启停与默认模型管理接口。
3. 租户可用模型查询接口。
4. 内部统一模型调用服务接口。

### 6.9.6 异常处理

1. 供应商不可用时切换兜底策略，不应泄露密钥信息。
2. 重试次数达到上限后写入失败日志。
3. Token 超限时调用前拦截。

### 6.9.7 测试点

1. 多供应商配置管理。
2. 不同用途的模型调用日志完整性。
3. Token 与成本统计正确性。
4. 失败重试与失败率统计。

## 6.10 会话记录与数据管理模块

### 6.10.1 模块职责

### 6.10.2 边界与依赖

1. 会话列表与详情接口。
2. 会话解决状态更新接口。
3. 数据导出接口。

### 6.10.6 异常处理

1. 权限不足时不得暴露敏感信息。
2. 导出任务量过大时建议异步导出。
3. 删除操作需支持软删或归档策略，避免误删不可恢复。

### 6.10.7 测试点

1. 会话列表与详情聚合完整性。
2. 敏感信息脱敏与授权查看。
3. 租户间数据导出、删除隔离。
4. 删除与导出行为审计留痕。

## 6.13 二期人工客服模块

### 6.13.1 模块职责

1. 承接访客转人工请求。
2. 管理坐席在线状态。
3. 执行排队与会话分配。

### 6.13.4 核心流程

1. 访客请求转人工或提交联系方式。

### 6.13.5 API 设计

1. 转人工请求接口。
2. 坐席状态切换接口。
3. 分配与接入接口。

### 6.13.6 异常处理

1. 无可用坐席时进入排队或待跟进。
2. 坐席掉线时需支持会话重新分配或结束。
3. 实时通道异常时需保证消息不丢失或可重发。

### 6.13.7 测试点

1. 转人工入口预留与待跟进记录。
2. 二期在线状态与分配策略。
3. 实时消息稳定性。

## 7. 跨模块流程设计

### 7.1 自动回答主流程

1. 访客入口完成 chatbot 与域名校验。
2. 对话编排校验租户状态、chatbot 状态、套餐额度。
3. 记录访客消息。
4. FAQ 优先匹配。
5. FAQ 未命中时执行知识库检索。
6. 命中知识片段后调用模型生成带引用回答。
7. 未命中时按策略决定是否进行纯模型回答。
8. 记录回答消息、模型日志、用量、引用来源。
9. 若失败则返回兜底话术，并在需要时创建待跟进记录。

### 7.2 chatbot 创建与上线流程

1. 租户创建 chatbot。
2. 配置外观和行为策略。
3. 导入 FAQ 与知识库。
4. 获取部署脚本和独立聊天页链接。
5. 通过预览和测试会话验证后启用。

### 7.3 文件知识入库流程

1. 上传文件并完成额度校验。
2. 保存文件元数据与原始文件。
3. 异步解析文本。
4. 切分片段并生成向量。
5. 写入知识片段与向量。
6. 更新状态供前端查询。

### 7.4 数据导出与删除流程

1. 权限校验。
2. 限定租户数据范围。
3. 生成导出结果或执行删除。
4. 写入审计日志。

## 9. 非功能设计

### 9.1 安全设计

1. 密码采用安全哈希算法存储。
2. 模型密钥采用加密保存或安全配置管理。
3. 后台接口统一鉴权，访客接口统一进行入口校验。
4. 敏感信息默认脱敏展示。
5. 文件上传限制类型、大小、路径和下载方式。
6. 网页抓取限制频率、超时和目标范围。
7. 所有租户级业务数据强制附带 `tenant_id`。

### 9.2 性能设计

1. 聊天接口应在 3 秒内返回首个结果或处理中状态。
2. FAQ 匹配目标 500ms 内完成。
3. 知识检索目标 1s 内完成。
4. 后台列表目标 2s 内完成。
5. 异步任务需支持重试与状态查询，避免前台长时间阻塞。

### 9.3 可用性设计

1. 模型失败时返回友好提示或兜底话术。
2. 文件解析失败、抓取失败需展示明确原因。
3. 超额度场景明确展示限制项。
4. 审计与日志需要支撑问题追踪。

### 9.4 国际化设计

1. 三类前端应用均支持中文和英文界面。
2. FAQ、知识库、欢迎语、行为策略应支持语言维度配置。
3. 统计和后台文案需统一语言资源键。

### 9.5 部署与运维设计

1. MVP 采用 Docker 单机部署。
2. 前端静态资源与后端 API 通过反向代理统一入口。
3. PostgreSQL 与 pgvector 统一部署在数据库服务内。
4. 文件存储采用本地磁盘目录并按租户隔离。
5. 需预留未来迁移对象存储和多实例部署的配置抽象。

## 10. 分阶段实现边界

### 10.1 MVP 必做

1. 多租户、认证权限、租户管理、套餐额度。
2. chatbot 配置、渠道部署、FAQ、知识库、对话编排。
3. 模型供应商配置与调用日志。
4. 会话记录、统计报表、审计日志。
5. 转人工入口和待跟进记录。

### 10.2 二期扩展

1. 实时人工客服。
2. 坐席排队与分配。
3. 工单沉淀。
4. 坐席效率、满意度、质检统计。

### 10.3 长期扩展预留

1. 在线支付与订阅续费。
2. 企业 SSO。
3. 多渠道接入。
4. 外部知识库 API 同步。
5. 多区域部署与高可用。

## 12. 结论

本详细设计将系统拆分为可独立实现和测试的业务模块，并明确了模块边界、依赖关系、核心流程和非功能约束。MVP 可以围绕“chatbot 配置 + 知识导入 + 自动回答 + 数据治理”形成完整闭环，二期则在现有会话和待跟进模型基础上扩展实时人工客服与工单能力。
