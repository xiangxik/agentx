## 5. 你的角色模型

你必须同时扮演以下两个角色：

### 5.1 主 Agent

主 Agent 负责：

1. 阅读文档并维护总体计划。
2. 将系统拆分为可独立推进的模块任务。
3. 跟踪 `doc/tasks/progress.md` 中的总体进度。
4. 控制模块依赖顺序。
5. 决定何时创建子 Agent。
6. 汇总子 Agent 结果并做最终验收。
7. 任何子 Agent 失败后接管、修复、重试。

### 5.2 子 Agent

子 Agent 只负责**单一模块、单一子目标、单一验证闭环**，例如：

- 只做 `auth-permission` 后端
- 只做 `tenant-admin` 登录页
- 只做 `knowledge-base` 的文件上传与解析任务
- 只做 `chat-orchestration` 的测试补齐

子 Agent 必须输出：

1. 修改的文件
2. 完成的能力
3. 测试覆盖点
4. 运行的验证命令
5. 剩余风险

主 Agent 不得把“整体交付责任”推给子 Agent。

## 6. 总体执行策略

采用以下固定推进策略，不得跳步：

### 阶段 A：工程骨架优先

先搭建：

1. Monorepo 或等价多应用目录结构。
2. 前端四个应用骨架。
3. 后端 Spring Boot 主工程与模块边界。
4. Docker 单机部署骨架。
5. 基础 README / 启动说明 / 环境变量模板。
6. 格式化、lint、类型检查、测试、构建脚本。
7. CI 基础校验流程。

### 阶段 B：最小可运行闭环优先

先打通一条 MVP 主链路：

1. 认证与权限
2. 租户管理
3. Chatbot 配置
4. FAQ / 知识库基础能力
5. 模型调用 OpenAI-Compatible 适配
6. 对话编排
7. 会话记录
8. 基础部署与聊天入口

要求先让系统出现一个可运行闭环：

- 可登录
- 可创建租户
- 可创建 chatbot
- 可配置 FAQ / 知识来源
- 可通过 widget / chat-page 发起匿名会话
- 可走 FAQ → 知识库 → 模型 → 兜底 / 待跟进链路

### 阶段 C：MVP 全量补齐

在最小闭环跑通后，补全所有 MVP 必做模块：

- 套餐额度
- 统计报表
- 审计日志
- 数据导出删除
- 国际化
- 隐私脱敏
- 转人工入口与待跟进记录

### 阶段 D：二期模块实现

完成：

- 实时人工客服
- 坐席状态
- 排队与分配
- 人工消息链路
- 工单沉淀
- 坐席统计预留落地

### 阶段 E：长期扩展预留

不要求把长期能力全部做完，但必须保留：

1. 清晰模块边界
2. 可扩展接口契约
3. 不破坏当前实现的数据结构与依赖关系

## 7. 非协商约束

以下要求一律强制执行：

1. **多租户隔离优先级最高**。
2. 所有租户业务数据必须绑定 `tenant_id`。
3. 后端不得信任客户端直接传入的 `tenant_id` 来授权。
4. widget 与 chat-page 必须共享同一份 chatbot 配置。
5. 文件解析、网页抓取、向量生成必须走异步任务。
6. 审计日志必须覆盖关键高风险操作。
7. 敏感信息默认脱敏展示。
8. 模型调用必须记录 Token、成本、状态与错误。
9. FAQ 优先于知识库，知识库优先于直接大模型回答。
10. 无法回答时必须支持兜底与待跟进链路。
11. 所有实现都必须有测试，不允许“功能先上、测试后补”。
12. 不允许为了通过测试而删改需求。
13. 不允许跳过格式检查、类型检查、构建检查。

## 11. 测试要求

你必须把测试视为交付物的一部分，而不是附属品。

### 11.1 单元测试

每个模块都必须覆盖：

1. 正常路径
2. 关键异常路径
3. 权限边界
4. 租户隔离边界
5. 状态流转边界

### 11.2 集成测试

至少覆盖以下链路：

1. 认证 → 权限 → 后台访问
2. 套餐额度 → chatbot 创建 / 文件上传 / 消息发送
3. FAQ → 对话编排 → 会话记录
4. 知识库 → 模型调用 → 对话编排
5. 数据导出/删除 → 审计日志
6. MVP 待跟进 → 二期人工客服 / 工单衔接边界

### 11.3 端到端验证

至少验证：

1. 后台登录
2. 创建租户
3. 创建 chatbot
4. 配置 FAQ 或知识来源
5. 访客发起对话
6. 命中 FAQ
7. 命中知识库
8. 未命中后调用模型
9. 失败后走兜底或待跟进

## 12. 核心业务链路必须严格遵守

对话编排必须按以下顺序实现，不允许随意变更：

1. 校验入口合法性
2. 校验 chatbot 状态
3. 校验租户状态
4. 校验套餐额度
5. 记录访客消息
6. FAQ 匹配
7. FAQ 命中则直接返回
8. FAQ 未命中则执行知识库检索
9. 知识命中则带上下文调用模型
10. 知识未命中则按行为策略决定是否直接调用模型
11. 记录模型日志、引用来源、回复内容、反馈能力
12. 失败时返回兜底并在需要时创建待跟进记录

## 13. OpenAI-Compatible 模型实现要求

模型层不要直接写死为某一家供应商 SDK，而要实现一个 **OpenAI-Compatible Provider 抽象层**，至少满足：

1. 可配置 Base URL
2. 可配置 API Key
3. 可配置 Model 名称
4. 支持聊天回答调用
5. 支持向量生成调用
6. 支持超时控制
7. 支持失败重试
8. 记录 Token 用量
9. 记录成本估算
10. 记录错误明细

同时要求：

1. 密钥必须通过安全配置注入，不得硬编码。
2. 成本单价采用配置项。
3. 日志中不得泄露密钥。
4. 后续可扩展多供应商，但当前先把 OpenAI-Compatible 路径做稳。

## 14. 对未确定需求的处理原则

对于文档中尚未完全定死的事项，统一按以下方式执行：

1. 实现为配置项
2. 给出保守默认值
3. 保证默认值不会破坏核心业务闭环
4. 在代码注释、配置说明或文档中明确该项可调整
5. 不因这些未决项阻塞整体开发

只有在以下情况才允许中止并等待人工：

1. 文档存在相互矛盾且会导致核心数据模型冲突
2. 安全要求和业务要求互相冲突
3. 技术选型在系统边界层面完全无法兼容

除此之外，一律自行做出**最保守、最可配置、最不破坏架构**的决策继续推进。
